Old defects fixed—5 of 14Better

Five of the fourteen defects from the previous report are genuinely fixed, and the four issues reported to me directly before this run — the admin live-session 403_COURSE_ENROLLMENT_GUARD, the stuck WebRTC overlay, AI quiz generation, and the blank student chatbot replies — are all confirmed working. The live-classroom tooling remains the strongest part of the product.

Against that, the platform has regressed overall. Nine defects that did not exist in the September 4 build are now present, and three of them are severe enough that I would not put this build in front of students:

1. A student can submit an empty assessment and be awarded 100%. The submission page renders no input fields at all, the button posts {answers:{}, files:[]}, and the record is stored as grading_status: "graded", grading_score: "100.00". This is not a display bug — it is what the admin KPI assessmentAvg: 100 is measuring.

2. Every student statistic is wrong. A freshly registered student enrolled in exactly one course is told they have 39 courses enrolled, their completed course is at 0%, and their grade is F. The backend already returns the correct figures (enrolled_courses: [1 id], completed_lessons: [1]); four pages ignore them and count the whole public catalogue instead.

3. Students cannot take a multiple-choice quiz through the UI. Assessments carry no type field, so every one of them is routed to the assignment upload page instead of the exam runner. The runner exists at /take and nothing in the interface ever links to it.

None of this is deep structural damage. Defects 1 and 3 are one missing field and one wrong route target; defect 2 is four pages reading the wrong endpoint. They are cheap to fix and expensive to leave.

3. Note on personas

The situation is unchanged from the previous report: two real personas, not three.

Registration is at /login?register=true and offers exactly three fields — Full Name, Email, Password. There is no role picker, and POST /v1/auth/register returned role: "student" for the account created during this run. On the admin side, the Students screen can move a user between student and admin and offers no third option. /instructor is not a route.

"Instructor" survives in three places, none of them an account you can sign in to:

  • The database does support it — users.role CHECK (role IN ('student','instructor','admin')) — and the seed file creates instructor@local.test. This is a change from September: the role is now real at the data layer, just unreachable from the UI.
  • The live-session header labels the host "Role: Instructor / Moderator".
  • Course pages show the instructor's real user name (now "Local Instructor", previously the hardcoded "Dr. Ahmed Hassan") — an improvement, but still display-only.

A consequence worth flagging: the admin dashboard's user breakdown reads "6 students · 1 admins" under a tile that says 8 TOTAL USERS. The missing one is the instructor. See DEF-17.

7. Verification notes

Results below were established by reading the deployed source or calling the API directly, not by observation alone.

7.1 — DEF-09, Settings: confirmed inert end to end

The save path writes localStorage["reali_admin_settings"] after an artificial 800 ms delay. The full stored object is {academyName, supportEmail, language, aiEnabled, aiModel:"gpt-4", aiPersonality, maintenanceMode, restrictEnrollment, twoFactorAuth, stripeKey, zoomClient}. Two independent confirmations that nothing consumes it:

  • reali_admin_settings, academyName and maintenanceMode each appear in exactly one file in the entire bundle — AdminSettings-DXNQs0ms.js, the settings page itself.
  • There are no settings routes anywhere in backend/routes/*.js.

The aiModel:"gpt-4" default is also misleading: the backend hardcodes qwen/qwen3.8-27b at three call sites (data.js:217, data.js:291, meetings.js:547), so the field cannot select a model even in principle.

7.2 — DEF-10, Calendar: a request-contract mismatch

The client sends {title, description, date, time, type:'custom'}. events.js:99-101 requires startsAt and rejects everything else with "Title and startsAt are required." No custom event can be created from the UI. The client then retries against a second endpoint (/v1/events), so a future fix to the payload would create each event twice.

The "Upcoming Custom Events" sidebar is separately unfixable as written: it filters on new Date(e.date) >= new Date, but the backend's formatEvent returns startDate/startsAt and no date field, so the predicate can never match.

7.3 — DEF-08, Course deletion: no confirmation exists

7.7 — DEF-02 vs assessments: an important distinction

The answer-key leak is specific to the AI quiz endpoint. GET /v1/assessments was checked live and returns questions with keys [id, text, prompt, type, options, marks, points, rubric] — no correct-answer field, matching the stripping at assessments.js:270. The AI quiz path (data.js:310-311) does the opposite and includes correct_answer and correctIndex in the 201 response the browser receives.

9. Recommendations

Ordered by what I would fix first, not by severity label.

  1. Stop awarding 100 for an empty submission. POST /assessments/:id/submit (assessments.js:370-386) inserts grading_status='graded', grading_score=100 without evaluating an answer. The scored path already exists at POST /attempts/:submissionId/submit — make the fallback grade properly or reject. Until then every average on the platform, including the admin KPI, is measuring this.
  2. Remove the answer key from the AI quiz response. data.js:310-311 puts correct_answer and correctIndex in the payload sent to the student. Strip them server-side and grade on submission, exactly as assessments.js:270 already does for real assessments. This is a two-line change.
  3. Add a type to assessments. One missing field is causing four visible failures: students are routed to an assignment page instead of the quiz runner, every row reads "TASK", and all four type filters read 0 on two screens. Add the column (or derive it from submission_type), return it, and default it to quiz.
  4. Point the student pages at enrolled_courses. The correct data is already returned by GET /v1/users/:id and is already access-controlled. Switching the Dashboard, Profile, Performance and My Courses pages from GET /data/projects to that endpoint fixes five failing scenarios at once. Then make the Dashboard read real progress — the API already returns progress:100 for the course it displays as 0%.
  5. Delete the hardcoded email gate on role management. goharhany@gmail.com in AdminStudents and AdminStudentProfile decides who sees the Promote/Demote buttons. The server already enforces requireRoles('admin') correctly, so the check adds no security — it only locks every other admin out of a feature they are authorised to use. Replace it with the role from the session.
  6. Put a confirmation back on course deletion. One click currently archives a course permanently from the admin's point of view, and the same control is reachable from Data Manager's Projects tab where the rows are bare UUIDs and the buttons have no labels. Restore the arm-then-confirm behaviour, and add the owner check that courses.js:262 already implements but data.js:52-56 omits.
  7. Fix the calendar payload, then the sidebar. Send startsAt (or accept date server-side) and drop the duplicate POST to /v1/events. Then change the sidebar filter to read startsAt — it currently tests a date property the API never returns, so it can never show anything. Add required to the title field while you are in there; blank submission is still a silent no-op.
  8. Either wire Settings to the backend or say plainly that it does nothing. Today an admin can enable Maintenance Mode, turn on 2FA, paste Stripe and Zoom keys, click Deploy, read "updated and deployed" — and change nothing for anyone, including themselves. That is worse than an obvious bug because it looks like it worked. If these controls are not on the roadmap, disable the screen and label it as not yet functional.
  9. Make the RAG counters honest. data.js:156-157 and :166 return constant 1 and 12 whether or not a file was attached. Return the real counts, and block the pipeline client-side when nothing is selected. The file upload itself works correctly — do not lose that while fixing the reporting.
  10. Give course pickers their titles back. Six screens present 39 raw UUIDs where a course name belongs, including the step-4 review an admin reads before publishing. The titles are already in the same API responses; this is a display-field substitution in the shared dropdown component.
  11. Fix the small contract breaks that produce fake successes. Three separate places report success while doing nothing: Create Assessment with "General (All Courses)", Inject Record with any course other than the literal "Global", and every message in Command Chat. Each is a value the backend cannot accept reaching a UI that reports success regardless. Validate on the server, surface the error, and never toast success on a failed write.
  12. Make Enter send, in both chats. Neither Command Chat nor Study Chat submits on Enter despite the input sitting inside a <form> with a type="submit" button. Verified twice per screen with focus confirmed. This is the single most-expected interaction on a chat screen.
  13. Then the polish pass. "Quizs" and "Live Classs" (fix the pluralization, not the string); $undefined, "· h total" and "( reviews)" on the course page; "Quiz undefined" cards; the dead /student/dashboard link on the 403 guard; "Your was submitted on —."; the missing success toast on both profile screens; aria-labels on the Data Manager icon buttons; clearing reali_user on logout; and a timeout for sessions stuck in live.
  14. Decide what "Instructor" means. The role is now real in the database and seeded, but unreachable from the product — no route, no role picker, no way to promote to it. Either surface it or stop describing three personas.
