2. How this pass was run

Three layers of evidence, in increasing order of fidelity:

  1. Automated API smoke test — backend/smoke-qa-fixes.mjs, 20 fetch-based assertions covering the defect-level behaviour (scoping, grading, validation, persistence). Run against the live server.
  2. Project test suite — npm test (node --test apps/web/tests/*.test.js).
  3. Browser retest — the actual failing scenarios re-driven in a real browser session against http://localhost:3001, capturing network calls, toasts, and rendered text. Each check recorded the request log so "nothing happened" could be distinguished from "the right thing happened".

Two personas were used: admin@local.test and student@local.test, plus a purpose-registered student with zero enrolments (qa.retest.1790845564@local.test). The zero-enrolment student is essential — the seeded student is enrolled in 84 courses, which makes scope defects invisible.

5. Open items and new observations

5.1 DEF-02 reopened — answer key shipped to the client High

The quiz generator was changed to return the key on purpose, with the rationale recorded in the source:

// Return the correct_answer (as string index) and explanation to the browser
// so the UI can provide instant feedback.
correct_answer: String(q.correctIndex),
explanation: q.explanation

This is a real integrity exposure: anyone can open devtools, read correct_answer for each question, and score 100% without knowing the material. It also makes the per-question explanation visible before the quiz is submitted.

The secure alternative is already built and passing. POST /v1/ai/quizzes/:quizId/grade holds the key in an ephemeral server-side map and returns {correct, total, score, detail}; the student quiz screen already calls it and reconciles the per-question review from detail. Reverting the two fields to server-only would restore instant-feedback accuracy without the leak — the only loss is that feedback arrives on submit rather than per click. This is a product decision, not a bug to fix unilaterally, so it is recorded here rather than changed.

5.2 Admin dashboard user breakdown does not add up Medium

The tile reads 18 TOTAL USERS with a breakdown of "16 students · 1 admins". Those sum to 17, and the missing account is the instructor — the breakdown has no instructor term at all. The 26 September report flagged the same shape ("6 students · 1 admins" under "8 TOTAL USERS"); the underlying omission was not addressed. Cosmetic, but it undermines confidence in the other numbers on that page.

5.3 A newly created course is invisible in the Courses list Medium

The DEF-18 fix creates the course correctly, but it defaults to status='draft', and GET /v1/courses returns published courses only (50 of them, every one published). So an admin clicks "+ New Course", sees a success toast and a page refresh, and the course is nowhere in the list — it looks like the creation failed. The draft is visible in the RAG Pipeline and Create Assessment pickers, which read /data/projects (76 non-archived courses). Either the admin list should include drafts with a status badge, or the creation flow should offer to publish immediately.

5.4 Enrolment count and course-list count disagree Low

student@local.test has 84 enrolment rows, but /data/projects returns 76 courses for the same student. The gap is 8 enrolments pointing at archived courses: the dashboard headline counts enrolments, the list counts joinable courses. Both numbers are individually defensible; showing them side by side is not.

5.5 Maintenance Mode still does nothing Low

Settings now persist to the database (A-SET-02 passes), but maintenanceMode, restrictEnrollment and twoFactorAuth are stored and never read by any request path. Toggling Maintenance Mode produces a durable record with no runtime consequence. Persisting the value is the prerequisite; enforcing it is still outstanding.

5.6 Validation is script-level only Low

No form field carries the HTML required attribute. Event and settings validation now produces clear messages and blocks the request (A-CAL-02, A-SET-01 both pass), but it lives in onClick handlers, so it is bypassed by anything that submits the form directly and gives no native browser affordance.

5.7 Minor items

  • Question count is not honoured at the API layer. A direct POST with num_questions:3 returned 5 questions; the browser flow requesting 3 returned 3. The UI sends a differently-named parameter, so users are unaffected, but the API contract is inconsistent.
  • Grade "F" for a student with no data. The Performance report shows an overall grade of F at 0% for a brand-new student. "No data yet" would be more accurate than a failing grade.
  • Registration now enforces name uniqueness. POST /v1/auth/register rejects a duplicate display name with USERNAME_TAKEN. This is new behaviour and it broke the smoke test, which reused a fixed name; the test now generates a unique one. Worth confirming this is intended — display names collide easily in real use, and the error message invites confusion with the email-uniqueness case.
  • Logout button not verified. The sidebar Logout control could not be scrolled into view under automation, so its click path was not exercised. Clearing storage does remove both reali_token and reali_user, so no stale identity survives a manual logout.

7. Data-quality notes

These are properties of the seeded database rather than code defects, but they distort anything measured against it:

  • 34 duplicate courses share the title "Advanced AI Architectures", each with a single lesson. Continue Learning therefore shows what look like duplicate cards. All 34 are at 0% for the seeded student.
  • 84 enrolments resolve to 76 courses — 8 point at archived courses.
  • 3 students are soft-deleted, so "students" is 15 or 18 depending on whether deleted_at is filtered. The command chat filters correctly; a raw COUNT(*) does not.
  • 42 published assessments, 3 of them platform-wide (course_id IS NULL). Those 3 are what every student sees regardless of enrolment — correct, but easy to mistake for a scoping failure.
  • Repeated test runs accumulate registrations. Anyone re-running the suite should expect the student count to grow.

8. Reproducing this pass

# 1. Start PostgreSQL (portable instance)
"C:\Users\Public\pgsql\bin\pg_ctl.exe" -D "C:\Users\Public\pgsql\data" \
    -l "C:\Users\Public\pgsql\pg.log" -w start

# 2. Apply migrations and start the backend
cd backend
node db/migrate.js
node server.js            # http://localhost:3001  (serves the SPA too)

# 3. Automated checks
node smoke-qa-fixes.mjs   # 19 pass / 1 fail  (the fail is DEF-02, by design)
cd .. && npm test         # 1 pass / 0 fail

The server verifies DATABASE_URL and exits non-zero if PostgreSQL is unreachable, so a 000 from curl http://localhost:3001/v1/health almost always means the database is down rather than the app being broken. backend/.env holds live credentials and must stay untracked.

Two things to be aware of before treating this as done.

1. The frontend has no source in this repository — apps/web/assets is a build artefact. Every frontend fix above is an edit to minified output. They are committed and they pass syntax checks, but the next real build will silently discard all of them. Recovering the source project is the single highest-value follow-up.

2. DEF-02 needs a decision. Either accept that the answer key is visible to students, or drop the two fields and rely on the server-side grading path that is already wired and passing.
